# Working on ArchDoc

ArchDoc models its own architecture in `.archdoc/`. Use it the way ArchDoc asks every user's agent to.

## Architecture model (ArchDoc): start here

This repository's architecture is modeled in `.archdoc/`: actors (who uses the system), elements (what it's made of, each mapped to code paths), journeys (how actors reach their goals), and data. People own the model. It's the fastest way to find where code lives and what a change affects, so use it before you search the code.

Every task: context, edit, check, seal. Each MCP tool has a CLI command of the same name. The MCP server and `npx @archdoc/cli` download the CLI from npm the first time; in a sandbox without network access (Codex's default) they exit with no output. That isn't an empty answer: rerun the command with network access, or ask the user to allow it.

1. Find where to start, before grepping: the `archdoc_context` MCP tool with the task in a few words, the files you plan to change, or both (for example "pr report shows type undefined for data fields"), or `pnpm -s archdoc context <words or paths>`. It returns the files and functions to open first, other code that does the same job (other callers of the functions they use, which a fix usually needs too), the data, rules, and journeys involved, the tests to run, owners, and who uses it, other repos included.
2. Name the affected journeys and actors when you share your plan. Ask the user before changing a critical journey, or removing or renaming anything another repo uses.
3. Look up any one thing with `archdoc_show` (or `pnpm -s archdoc show <id>`): an element (with its code), actor, journey, data entry, `Entry.field` (its lineage), Triage record, or a fact `archdoc_check` names. `archdoc_find` (or `pnpm -s archdoc find`) lists parts of the model by words, by place (`under`), by the file they own (`path`), or by what they lack (`missing`), and `outline: true` shows its element tree, so you don't read the YAML to find IDs.
4. Edit the model with the code, by ID with `archdoc_edit` (or `pnpm -s archdoc edit '<ops as JSON>'`) rather than by hand: `add`, `set` (a JSON merge patch), `remove`, `rename` (moves an element and rewrites every reference), `use`, and `step` ops, many per call, all written or none, each changing only its own lines; it refuses an edit that would add errors, and says what it fixed and broke. Add a component or a dependency you meant to add with `by: agent:<your-name>`, which marks it `provenance: { source: suggested }`; update the model in the same change if you moved or removed one; update `data:` and the `sends`, `accepts`, `returns`, or `stores` that name it if a component's data changes, and classify sensitive fields (`classification: pii`). Elements in other repos are referenced by namespace (`payments.charges`); to depend on a new repo, add it to `imports` in `archdoc.yaml` and run `pnpm -s archdoc sync`. Never edit `.archdoc/archdoc.lock` or `.archdoc/vendor/` by hand.
5. Check: `archdoc_check` with base "main", or `pnpm -s archdoc check --base main`. It gives the verdict the PR comment will give, and what your change introduced, each with its fix: imports the model doesn't declare, broken rules and journeys, stale paths, data rules, Triage records, and facts whose code changed since they were sealed. Fix those; if a new dependency isn't intended, remove the import.
6. Seal: for each fact whose code changed, read what changed, update the model if it no longer describes the code, then seal it with `archdoc_seal` or `pnpm -s archdoc seal <fact> --by agent:<your-name>`. It says what's still to check. Never seal a fact you haven't read: reviewers see what you sealed in the PR.

In the PR description, list the affected journeys and actors and the model changes you suggested. `pnpm -s archdoc report --base main` (or `archdoc_check` with `format: "markdown"`) writes this for you.

When you're handed a bug to explain or fix (an issue, a log line, a stack trace, wrong output), triage it to its root cause first, also when you're asked to fix it: start a Triage record with `archdoc_triage` and `symptom` set to the bug as given (or `pnpm -s archdoc triage start bug.txt`), before you read the code. Its answer says where to start and how to fill the record in, hop by hop, with evidence, until `status: root-caused`; if you fix it, set `status: fixed` and `fix`, and commit the record with the fix. `archdoc_triage` with `wait: true` picks up a bug the user sent from the explorer's Triage tab. The full workflow is the archdoc skill's `references/triage.md` ([on GitHub](https://github.com/ArchDoc/archdoc/blob/main/integrations/claude-plugin/skills/archdoc/references/triage.md)).

When you're asked to plan, design, or think through a change before it's built, plan it with the user on the model instead of writing a markdown plan: start one with `archdoc_plan` (`action: start` with the idea, or `pnpm -s archdoc plan start <idea>`), which writes `.archdoc/plans/<id>.yaml`; open the explorer's Plan tab for them (`pnpm -s archdoc view --detach --watch --open`), where they click on the map to add a box (New element) or a note (New note) and say what they want there (an intent, `i1`), and each one comes to you as they add it. They drive the design: suggest nothing before they've sent an intent. Wait for it (`action: wait`), check each intent against the code, and answer with `action: respond`: suggested changes and sequences that carry out what it says, no more, each with `for: ["i1"]`, a question on the intent with `options` they tap where it leaves a design choice open (instead of choosing for them), and notes (insight, risk), never edits to their items, which they accept or dismiss; a box they drew is theirs, so suggest what it needs beside it. It's a conversation, a turn each: answer what's new briefly, one question at a time, and wait again at once. Repeat until nothing's open and they mark it ready, then write the tasks that carry it out (each with the changes it makes, files, and tests) and carry them out in order, editing the model as each lands and setting each task's status (`action: task`). The full workflow is the archdoc skill's `references/plan.md` ([on GitHub](https://github.com/ArchDoc/archdoc/blob/main/integrations/claude-plugin/skills/archdoc/references/plan.md)).

In a repository with no `.archdoc/` yet, including when you're asked to figure out or explain its architecture, the answer is a model of the whole system written to `.archdoc/`, however big the repository: run `archdoc_init` (or `pnpm -s archdoc init`) for real, then reshape, describe, connect, and trace what it wrote with `archdoc_edit` and `archdoc_find`, until `archdoc_check` with `done: true` (or `pnpm -s archdoc check --done`) says the model is done; then ask a person to review it. Don't stop after init or partway to summarize, hand over part of it, or ask whether to go on. Init's answer lists the steps; before you start, read the archdoc skill's `references/init.md` (in `.agents/skills/archdoc/` or `.claude/skills/archdoc/` when it's installed, else [on GitHub](https://github.com/ArchDoc/archdoc/blob/main/integrations/claude-plugin/skills/archdoc/references/init.md)), which says how to shape a model a newcomer reads top-down in ten minutes.

The MCP server is configured in `.mcp.json` and runs from the build, so run `pnpm build` first.

## Build and test

- Node 22.12+ and pnpm 10. `pnpm install`, then `pnpm build`.
- Before pushing: `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm -s archdoc validate --strict`.
- `@archdoc/core` stays deterministic: no LLM calls, no network. CLI, MCP, the explorer, and the Action are thin layers over core. MCP, the explorer, and the Action never depend on each other; the CLI serves the explorer and starts MCP, and the Action runs the CLI.
- Add a changeset (`pnpm changeset`) for changes to published packages. Commit messages follow Conventional Commits.
