## Architecture model (ArchDoc): start here

This repository's architecture is modeled in `.archdoc/`: actors (who uses the system), elements (what it's made of, each mapped to code paths), journeys (how actors reach their goals), and data. People own the model. It's the fastest way to find where code lives and what a change affects, so use it before you search the code.

Every task: context, edit, check, seal. Each MCP tool has a CLI command of the same name. The MCP server and `npx @archdoc/cli` download the CLI from npm the first time; in a sandbox without network access (Codex's default) they exit with no output. That isn't an empty answer: rerun the command with network access, or ask the user to allow it.

1. Find where to start, before grepping: the `archdoc_context` MCP tool with the task in a few words, the files you plan to change, or both (for example "pr report shows type undefined for data fields"), or `archdoc context <words or paths>`. It returns the files and functions to open first, other code that does the same job (other callers of the functions they use, which a fix usually needs too), the data, rules, and journeys involved, the tests to run, owners, and who uses it, other repos included.
2. Name the affected journeys and actors when you share your plan. Ask the user before changing a critical journey, or removing or renaming anything another repo uses.
3. Look up any one thing with `archdoc_show` (or `archdoc show <id>`): an element (with its code), actor, journey, data entry, `Entry.field` (its lineage), Triage record, or a fact `archdoc_check` names. `archdoc_find` (or `archdoc find`) lists parts of the model by words, by place (`under`), by the file they own (`path`), or by what they lack (`missing`), and `outline: true` shows its element tree, so you don't read the YAML to find IDs.
4. Edit the model with the code, by ID with `archdoc_edit` (or `archdoc edit '<ops as JSON>'`) rather than by hand: `add`, `set` (a JSON merge patch), `remove`, `rename` (moves an element and rewrites every reference), `use`, and `step` ops, many per call, all written or none, each changing only its own lines; it refuses an edit that would add errors, and says what it fixed and broke. Add a component or a dependency you meant to add with `by: agent:<your-name>`, which marks it `provenance: { source: suggested }`; update the model in the same change if you moved or removed one; update `data:` and the `sends`, `accepts`, `returns`, or `stores` that name it if a component's data changes, and classify sensitive fields (`classification: pii`). Elements in other repos are referenced by namespace (`payments.charges`); to depend on a new repo, add it to `imports` in `archdoc.yaml` and run `archdoc sync`. Never edit `.archdoc/archdoc.lock` or `.archdoc/vendor/` by hand.
5. Check: `archdoc_check` with base "main", or `archdoc check --base main`. It gives the verdict the PR comment will give, and what your change introduced, each with its fix: imports the model doesn't declare, broken rules and journeys, stale paths, data rules, Triage records, and facts whose code changed since they were sealed. Fix those; if a new dependency isn't intended, remove the import.
6. Seal: for each fact whose code changed, read what changed, update the model if it no longer describes the code, then seal it with `archdoc_seal` or `archdoc seal <fact> --by agent:<your-name>`. It says what's still to check. Never seal a fact you haven't read: reviewers see what you sealed in the PR.

In the PR description, list the affected journeys and actors and the model changes you suggested. `archdoc report --base main` (or `archdoc_check` with `format: "markdown"`) writes this for you.

When you're handed a bug to explain or fix (an issue, a log line, a stack trace, wrong output), triage it to its root cause, also when you're asked to fix it: the record comes first, before you read the code, and these steps and `archdoc_triage`'s answer are the whole workflow (you don't need to find a skill file):

1. Start a Triage record: `archdoc_triage` with `symptom` set to the bug as given (and `title`, `link`, `reportedBy` when you know them), or `archdoc triage start bug.txt` (or `-` for stdin). It places the error on the journey steps it most likely showed up in, writes `.archdoc/triage/<id>.yaml` with status `investigating`, the best `expands: <journey>#<step>`, the elements the error names as open `hypotheses`, and steps from the stack, and says where to start.
2. Follow the code from there and fill the record in: rule each lead in or out (`verdict: confirmed` or `ruled-out`, with `evidence` and a `note`), one step per hop the failing request took with `action`, a `description` of what happened at that hop in the failing run (the value it had, what the code did with it, and why that's right or wrong there), what it carries (`sends`: the data entry, by its name under `data:`; `creates` or `changes` for a write), `code`, `role` (cause, spreads, symptom), and `evidence` (`reproduced` if you saw it run, `read` if you followed it in the code, `inferred` otherwise), `observed`/`expected` values on that entry's fields where they differ (`Order.status`), and `missing` for a call that didn't happen. A record is evidence of one bug, not the design: it's never part of the model.
3. Set `root-cause: { summary, step }` and `status: root-caused`; stop there if you were asked only to explain it. If you fix it, keep the record: set `status: fixed` and `fix: { summary, link, test }`. A fix without its record isn't done.
4. `archdoc_check` checks it: fix unknown elements, stale code references, and what the status still needs. A hop the model doesn't declare is drift you found while debugging, so mention it.
5. Commit the record with the fix, so the PR says which bug it fixes.

When you're asked to plan, design, or think through a change before it's built, plan it with the user on the model instead of writing a markdown plan: start one with `archdoc_plan` (`action: start` with the idea, or `archdoc plan start <idea>`), which writes `.archdoc/plans/<id>.yaml`; open the explorer's Plan tab for them (`archdoc view --detach --watch --open`), where they sketch the change on the map with the intent of every element, arrow, and step and press Send to agent; wait for it (`action: wait`), review every item against the code, and answer with `action: respond`: notes (insight, question, risk) and suggested changes and steps, never edits to their items, which they accept or dismiss. Repeat until nothing's open and they mark it ready, then write the tasks that carry it out (each with the changes it makes, files, and tests) and carry them out in order, editing the model as each lands and setting each task's status (`action: task`).

In a repository with no `.archdoc/` yet, including when you're asked to figure out or explain its architecture, the answer is a model written to `.archdoc/`, of the whole system, however big the repository: don't stop after init or partway to summarize, hand over part of it, or ask whether to go on. Run `archdoc_init` (or `archdoc init`) for real, not as a dry run, which writes nothing. It starts a model from its packages, compose services, imports, schema files, and Terraform and CDK, every fact marked inferred, leaving out tests and other verification code. It sweeps the layers inside one system: containers, the components inside each container, and the uses between them at each level, plus the tables, queues, and environments the infrastructure as code declares, and answers with the docs, deployment files, and entry points to start from. That's raw material: reshape it into a model a newcomer can read top-down in ten minutes, with `archdoc_edit`, a step of work per call, and `archdoc_find` (`outline`, and `missing` for what's left) rather than reading and editing the YAML. Read the README, the docs, and the files that wire the system (compose, Kubernetes, Helm, Terraform, app hosts, entry points), and make the parts they name the top-level elements, all inside the one `kind: system` element named for the product (only externals sit beside it, so the Context view differs from the Container view; `archdoc_edit` `add` puts a new container there for you). Name each element the way the code names that part: its directory, package, or module (code in `src/auth/` is `auth`, not `identity`), with the domain's words in the description; when its code goes by several names, give it a `name:` in plain words, such as `name: Local Migration Scripts`, not a coined kebab-case term. Keep each level to about 3 to 12 elements. Give a big container (dozens of files across several directories) components, and keep a small one (fewer than about five source files) lean, with none. Fold build config into the element it configures, give each component 1 to 5 code elements at the functions or classes a newcomer opens first (`kind: code`, `code: path#symbol` or `path:40-88`, never a whole file and never one per file; the explorer lists them in the component's details with links to the code, not on the map), so a reader can audit the model against those lines, group variants of one thing (one server in many languages) into one element, make one app's packages (a UI workspace's app and modules) one container, put a binary's own packages in its container rather than a separate `core`, rename elements named after build files, and leave tests, mocks, fixtures, benchmarks, and smoke checks out of the model. Add the datastores, queues, and externals (`kind: external`) init can't see, with each deployment definition mapped to what it deploys. Put uses between components, and send messages through the queue. For every element nothing connects to, find how it's reached at runtime (a URL from config, a queue topic, a CronJob, a plugin registry) and add the use the code shows. Then describe each container and component, top-down, keeping each layer nested inside the one above (`kind: component` inside a container, `kind: code` with `code: { path, symbol }` inside a component). Add actors from the entry points (`archdoc_paths`, or `archdoc paths`, lists the routes, consumers, scheduled jobs, and CLI commands, and the calls each makes; in a big repository it summarizes them by place and resource, and `entry` lists one group), (`person`, `role`, `team`, or `organization` for people; `system` for software that calls in on its own, such as another service or a scheduler; `agent` only for an AI agent), each with a `name:` in plain words (`name: Dashboard User`, not `dashboard-user`: kebab-case is for names in the code and infrastructure), and trace a journey for each main flow, so together they reach most entry points: a step per hop, each starting where the flow already is (when you don't know how it gets from one element to the next, read the code until you do, never jump), on the most specific element, each with an `action`, the `code` where it happens (the function, `file#function`, or lines, `file:40-88`, not a whole file), and what it carries across a boundary (`sends`, `creates`, `changes`, described under `data:` with a short name, such as `OrderPlaced`, a description, and its fields from where the code defines it: a schema file as `source:`, or the type the code builds). Say what each datastore stores, and where each part runs (`environments:`, `deploy:`), each on the most specific node, with the same nesting in every environment (`production.aws.lambda`, never `production` for one function and `production.aws.lambda` for another). A first pass usually shows dozens of errors and warnings: that's the work list, each with its fix, not a reason to stop or report. Never give a component to each file: a component is a directory's worth of one responsibility. Run `archdoc_check` with `done: true` (or `archdoc check --done`) until it says the model is done, fixing its warnings too (a missing schema or type means finding it in the code and mapping its fields) and leaving only those it says need a person (never add a use the code doesn't show just to clear a line), and ask a person to review it. Then ask whether they'd like to see it in the explorer, and if so open it with `archdoc view --detach --watch --open`, which prints the URL and returns (run again, it gives the URL of the one already running).
